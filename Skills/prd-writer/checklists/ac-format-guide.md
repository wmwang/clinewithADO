# AC (Acceptance Criteria) 格式指南

## 黃金格式

```
Given <前提 / 初始狀態>
When <使用者動作 / 系統事件>
Then <可觀察的結果>
```

- **Given**：場景的起點，要寫得夠具體讓 QA 可以重現
- **When**：單一動作，避免複合（「點 A 再點 B」拆兩條 AC）
- **Then**：結果必須是**外部可觀察**的（UI 變化、API 回應、DB 狀態），不是內部實作

## ✅ 好範例

### 範例 1（前端）
```
AC-1.1: Given 使用者已登入且是「客服主管」角色
When 進入工單列表頁
Then 看到「批次匯出」按鈕，位置在頁面右上角
```

### 範例 2（API）
```
AC-2.1: Given 呼叫者提供合法 PAT 但無 Read 權限
When 呼叫 GET /api/workitems/123
Then 回應 HTTP 403，body 包含 errorCode = "FORBIDDEN"
```

### 範例 3（效能）
```
AC-3.1: Given 資料庫有 10 萬筆工單
When 使用者搜尋任一關鍵字
Then P95 回應時間 ≤ 800ms（從 API Gateway 統計）
```

## ❌ 壞範例與修正

### 壞：太抽象
```
AC: 讓使用者體驗更順暢
```
**為什麼壞**：沒有前提、沒有動作、結果不可觀察、不可測。

**修正**：
```
AC: Given 使用者在工單詳情頁
When 點擊「返回列表」
Then 回到原先的列表頁且保留之前的篩選條件與捲動位置
```

### 壞：混入實作
```
AC: Given 使用者點擊送出
When 呼叫 saveWorkItem() 函式
Then Redis cache 被更新
```
**為什麼壞**：`saveWorkItem()` 是實作細節，Redis cache 是內部狀態。

**修正**：
```
AC: Given 使用者填完必填欄位
When 點擊「送出」
Then 畫面顯示「儲存成功」訊息，且重新整理後資料仍存在
```

### 壞：複合動作
```
AC: When 使用者填表單、上傳附件、送出，並收到 email
Then 工單建立
```
**為什麼壞**：一條 AC 塞 4 個動作，無法判斷哪步失敗。

**修正**：拆成 4 條 AC-x.1 ~ AC-x.4，各自獨立。

### 壞：缺量化
```
AC: 搜尋要快
```
**修正**：加數字，如「P95 ≤ 500ms」、「首屏 < 2 秒」。

## 常見情境對應

| 需求類型 | Given 範例 | Then 範例 |
|----------|-----------|----------|
| 權限控制 | 使用者為角色 X | 看到 / 看不到 某元件 |
| 表單驗證 | 欄位填入 `...` | 顯示錯誤訊息 `...` |
| 錯誤處理 | 後端回 500 | UI 顯示 toast「系統忙碌」 |
| 效能 | N 筆資料 | P95 ≤ X ms |
| 整合 | 第三方 API 回 X | 系統行為 Y |

## 給 AI 的提醒

當 PM 給出的 AC 不合格時，**不要自己補完**，而是用以下話術追問：

- 「這條 AC 的『前提』是使用者在哪個頁面 / 什麼狀態？」
- 「『Then』的結果如果要讓 QA 驗證，他會看到或點到什麼具體的東西？」
- 「這個結果有量化指標嗎？例如幾秒內、正確率多少？」
